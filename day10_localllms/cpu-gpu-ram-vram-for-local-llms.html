Day 10 · Local LLMs

CPU, GPU, RAM & VRAM: what really happens when a local LLM runs

When you type ollama run llama3.1:8b, about 5 GB of numbers travel from your SSD into memory, then into the graphics card. Billions of multiplications run for every word the model writes. This page follows that path one step at a time, starting from what a "bit" is.

🧑‍🍳
CPU

A few very smart workers. Good at complicated, step-by-step tasks.

🏭
GPU

Thousands of simple workers. Good at the same small task done many times at once.

🗄️
RAM

The CPU's work table. Big, but slower to read from.

⚡
VRAM

The GPU's own work table. Smaller, but much faster to read from.

Think of a restaurant kitchen. The SSD is the warehouse, where everything is stored but far away. RAM is the kitchen's pantry. VRAM is the counter right next to the cooks. The CPU is a head chef who can cook anything, but alone. The GPU is a line of 10,000 helpers who can only chop, but all chop at the same time. An LLM is a recipe that needs billions of chops for every word, so the helpers win, as long as the ingredients are on their counter.

What you'll be able to answer at the end

  • Why does an 8B model run fast on one PC and slowly on another?
  • Why does VRAM size matter more than how many GPU cores you have?
  • What does Ollama mean by 100% GPU or 45%/55% CPU/GPU?
  • Why does a longer chat use more memory?
  • How do I work out whether a model will fit on my computer?
Level 0 · Foundations

Bits, bytes & transistors

Everything in a computer, including your photos, this web page and an LLM, is stored as bits. A bit is a single 0 or 1. Inside the chip, a bit is a tiny switch called a transistor, which is either off (0) or on (1). Modern chips have tens of billions of transistors. An RTX 4090 GPU has about 76 billion.

UnitSizeExample
1 bit0 or 1One switch
1 byte8 bitsOne letter, like "A"
1 KB (kilobyte)~1,000 bytesA short text message
1 MB (megabyte)~1 million bytesA photo
1 GB (gigabyte)~1 billion bytesA 4-bit 1.5B model; ⅕ of an 8B model
1 TB (terabyte)~1,000 GBA typical SSD

How numbers are stored

An LLM is mostly a giant list of decimal numbers called weights (for example, 0.0213 or -1.402). How many bits each number uses decides both how accurate it is and how much memory it takes:

FormatBits per numberBytesUsed for
FP32 (float 32)324Classic training, very precise
FP16 / BF16162Modern training and "full quality" models
INT8 / Q881Nearly lossless compression
Q4 (4-bit)~4.5–5~0.6Default for most Ollama models
Key idea: memory needed = how many numbers × bytes per number. An 8-billion-parameter model at 2 bytes each needs 16 GB. At ~0.6 bytes each (4-bit) it needs about 5 GB. Almost everything later on this page builds on this one line.

What a "clock" is

Chips do work in beats, like a drummer keeping time. A 3 GHz clock means 3 billion beats per second. On each beat, every core can do one or more small operations, such as an add or a multiply.

Level 1 · Processors

The CPU, inside out

The CPU (Central Processing Unit) is the general manager of your computer. It runs Windows, your browser, Python and the Ollama program itself. It is built to finish one complicated task as fast as possible.

Cores

Independent "brains" on one chip. Typical laptops and desktops have 4–24 cores. Each core can run its own program.

Threads

With hyper-threading / SMT, one core can juggle 2 instruction streams, so an 8-core CPU shows 16 threads. For LLMs, physical cores are what count.

Cache (L1 / L2 / L3)

Tiny, ultra-fast memory built into the chip: KBs to tens of MBs. It keeps recently used data close to the cores so they don't have to wait for RAM.

SIMD units (AVX2, AVX-512, NEON)

Special instructions that do 8–16 multiplications in one go. llama.cpp (the engine inside Ollama) relies on these to run models on the CPU at a usable speed.

How a core works: fetch → decode → execute

  1. Fetch: get the next instruction from memory (for example, "multiply these two numbers").
  2. Decode: work out what the instruction means.
  3. Execute: the ALU (Arithmetic Logic Unit) does the math.
  4. Write back: store the result in a register (the fastest memory of all, inside the core).

CPU cores also do clever things like branch prediction (guessing which if branch comes next) and out-of-order execution. That makes them excellent for ordinary programs full of decisions. LLM math has almost no decisions. It's just multiply-and-add, billions of times over.

What the CPU does during local LLM use

  • Runs the Ollama server and handles your request (HTTP on localhost:11434).
  • Reads the model file from disk and tells the GPU what to do.
  • Tokenizes your text (splits it into token IDs) and turns tokens back into text.
  • Runs the layers that didn't fit in VRAM, or the whole model if there's no GPU.
Level 1 · Processors

The GPU, inside out

The GPU (Graphics Processing Unit) was built to color millions of screen pixels 60+ times a second. Coloring a pixel is a small, identical math job, so GPUs were built with thousands of simple cores that all run the same instruction on different data. This is called SIMT (Single Instruction, Multiple Threads). The same design turned out to be perfect for neural networks.

SMs (Streaming Multiprocessors)

The GPU is split into blocks called SMs. An RTX 4060 has 24 of them and an RTX 4090 has 128. Each SM has its own cores, cache and scheduler.

CUDA cores / shader cores

Simple math units: ~3,000 on an RTX 4060, ~16,000 on an RTX 4090. Each one is weaker than a CPU core, but there are a lot of them.

Tensor cores

Special units that multiply small matrices (for example, 16×16 blocks) in one step. This is where most AI speed comes from.

Warps

Threads run in groups of 32 that execute the same instruction in lockstep. GPUs hide memory delays by quickly switching to another warp while one waits.

CPUGPU
Number of cores4–24 powerful coresThousands of simple cores
Designed forLow latency: finish one task fastHigh throughput: finish many tasks at once
Good atDecisions, branching, OS, logicThe same math on huge arrays (pixels, matrices)
Memory it usesSystem RAM (~50–120 GB/s)Its own VRAM (~250–1,000+ GB/s)
Rough math power~1–3 TFLOPS~15–80 TFLOPS (more with tensor cores)

TFLOPS = trillions of floating-point operations per second.

CPU vs GPU: a parallel race

Job: do 1,024 small multiplications. The CPU has 8 fast cores, each finishing 1 multiplication per tick. The GPU has 512 slower cores, each needing 3 ticks per multiplication. Who wins?

CPU · 8 fast cores
Ticks: 0
GPU · 512 slow cores
Ticks: 0

The GPU finishes in 6 ticks; the CPU needs 128. Each GPU core is slower, but 512 of them working at once win easily. One LLM layer is millions of these independent multiplications, which is why GPUs suit it so well.
Level 2 · Memory

The memory ladder

Processors are incredibly fast, and memory struggles to keep up. Computers solve this with a ladder of storage: the closer to the core, the faster and smaller it is.

Two different "speeds": Latency is how long until the first byte arrives (like how long the delivery truck takes to show up). Bandwidth is how many bytes per second once the data is flowing (how big the truck is). LLM generation depends almost entirely on bandwidth, because every word needs the whole model read through. That's why VRAM wins, even though its latency is no better than RAM's.
Level 2 · Memory

RAM: the system's working memory

RAM (Random Access Memory) holds everything currently running: Windows, Chrome, VS Code, Python and the model weights the CPU is using. It is volatile, meaning it is wiped when the power goes off. That's why the model has to be loaded from SSD every time.

How RAM works

System RAM is DRAM. Each bit is a tiny capacitor that holds a charge (1) or not (0). The capacitors leak, so they are refreshed thousands of times a second. The memory sticks (DIMMs) connect to the CPU through memory channels, and each channel is a 64-bit-wide road.

Calculating RAM bandwidth

# bandwidth = transfers per second × 8 bytes per channel × number of channels
DDR4-3200, dual channel: 3200 MT/s × 8 B × 2 = 51.2 GB/s
DDR5-5600, dual channel: 5600 MT/s × 8 B × 2 = 89.6 GB/s
DDR5-6000, single stick: 6000 MT/s × 8 B × 1 = 48 GB/s   ← one stick halves your LLM speed!
Practical tip: for CPU-only LLMs, use two matching RAM sticks (dual channel), not one big stick. Two 8 GB sticks give about twice the LLM speed of one 16 GB stick.

What RAM holds while Ollama runs

  • Your operating system and apps: often 4–8 GB already in use.
  • The Ollama server program.
  • The model file, memory-mapped (mmap): the OS loads parts of the file into RAM as they are needed.
  • Any layers running on the CPU, plus their share of the KV cache.
When RAM runs out, Windows starts using the SSD as fake RAM (the page file, also called "swap"). The SSD is about 20× slower than RAM, so generation drops to a crawl: maybe 1 word every few seconds.
Level 2 · Memory

VRAM: the GPU's private, high-speed memory

VRAM (Video RAM) is memory soldered onto the graphics card, right around the GPU chip. The GPU cores can only work at full speed on data that is in VRAM.

Why VRAM is so much faster than RAM

  • Much wider road: system RAM is 128 bits wide (dual channel). A GPU uses a 128–384-bit bus, and HBM (data-center GPUs) uses 4096+ bits.
  • Faster signaling: GDDR6/GDDR6X/GDDR7 chips send 14–28+ Gbit/s on each wire.
  • Very short distance: the chips sit a few centimeters from the GPU on the same board.
# bandwidth = bus width (bits) ÷ 8 × data rate per pin
RTX 4060   (128-bit, 17 Gbps):  128/8 × 17 = 272 GB/s
RTX 3060   (192-bit, 15 Gbps):  192/8 × 15 = 360 GB/s
RTX 4090   (384-bit, 21 Gbps):  384/8 × 21 = 1008 GB/s
# compare: dual-channel DDR4 system RAM ≈ 51 GB/s

What lives in VRAM during inference

1. Model weights

The biggest part: every layer that was offloaded to the GPU.

2. KV cache

The model's "memory" of the conversation so far. It grows with context length.

3. Compute buffers

Scratch space for in-between results, plus the CUDA/driver context (~0.5–1 GB).

Why VRAM size is the #1 spec for local LLMs: GPU cores are useless if the weights aren't in VRAM. Whatever doesn't fit gets pushed back to the CPU and RAM, which are about 5–20× slower.
Level 2 · Connections

PCIe and unified memory

On a normal PC, the CPU+RAM side and the GPU+VRAM side are two separate worlds, connected by the PCIe bus (the slot your graphics card plugs into).

  • PCIe 3.0 x16 ≈ 16 GB/s, PCIe 4.0 x16 ≈ 32 GB/s. That is fine for loading a model once (5 GB in under a second), but far too slow to stream weights for every token.
  • That's why the model is copied into VRAM once and then stays there. Ollama keeps it loaded for 5 minutes after your last message by default (OLLAMA_KEEP_ALIVE).
  • While generating, only tiny data crosses PCIe: token IDs going in, and a few numbers coming out per token.

Unified memory (Apple Silicon Macs, some new AI laptops)

On an M1–M4 Mac, the CPU and GPU share one pool of memory on the same chip package. There's no PCIe copy and no separate VRAM, so a 32 GB Mac can give roughly 20–24 GB to the GPU. Bandwidth ranges from ~100 GB/s (base M-series) to 400–800 GB/s (Max and Ultra chips). This is why Macs with lots of memory are popular for running big models.

Integrated graphics (Intel/AMD laptop GPUs) also share system RAM, but at normal RAM speed (~50–100 GB/s), so they speed up math but not memory reads. Ollama mostly uses NVIDIA (CUDA), AMD (ROCm) and Apple (Metal) GPUs. On other machines it falls back to the CPU.
Level 3 · LLMs

What a model actually is in memory

A model file (Ollama uses the GGUF format) is basically:

  1. A header: the architecture, number of layers, vocabulary, chat template and so on.
  2. The tokenizer: a list of ~32k–256k text pieces (tokens), each with an ID.
  3. Tensors: big grids of numbers (the weights), grouped into layers.

Example: Llama 3.1 8B

PartShape / countWhat it does
Token embedding128,256 tokens × 4,096 numbersTurns a token ID into a vector of 4,096 numbers
32 transformer layers~218M weights eachAttention (which earlier words matter?) + feed-forward network (what do I know about this?)
Output head4,096 × 128,256Turns the final vector into a score for every possible next token
Total~8.0 billion parameters
The layers are like 32 stations on an assembly line. Each token's vector passes through station 1, then 2, all the way to 32. At each station it gets refined a bit more. To make one new token, the vector has to pass through every station, so every weight is read once per token.
Level 3 · LLMs

Quantization: shrinking the model to fit

Quantization stores each weight with fewer bits. For example, instead of 16 bits per weight, you store 4-bit values plus a small "scale" number for each block of 32 weights. The quality loss is small, and the memory saving is huge. When you ollama pull llama3.1:8b, you get a Q4_K_M version by default.

Q5_K_M5.75.7 GB50 GBVery good
Q4_K_M (Ollama default)4.84.9 GB43 GBGood: the best balance
Q2_K / Q32.6–3.93–4 GB26–34 GBNoticeably worse
# rule of thumb
model size (GB) ≈ parameters (billions) × bits per weight ÷ 8
8B × 4.8 ÷ 8 ≈ 4.8 GB      (+ KV cache + ~1 GB overhead to run)
Quantization helps twice: the model fits in less memory, and it runs faster, because fewer bytes have to be read for every token.
Level 3 · LLMs

The math inside a layer: why it's all matrix multiplication

Each layer mostly multiplies the token's vector (4,096 numbers) by big weight matrices. For example:

[ x1 x2 ... x4096 ]  ×  W (4096 × 14336)  =  [ y1 y2 ... y14336 ]
# each output y = x1·w1 + x2·w2 + ... + x4096·w4096   → 4,096 multiply-adds
# 14,336 outputs × 4,096 = ~58.7 million multiply-adds for just ONE matrix

All of those outputs are independent, so they can be computed at the same time. That's exactly the job thousands of GPU cores and tensor cores are built for.

How much math per token?

A useful rule: about 2 operations per parameter per token (one multiply and one add). So an 8B model needs ~16 billion operations for every token it writes.

Two phases, two different bottlenecks

⚡ Prefill (reading your prompt)

All prompt tokens are processed together: a matrix × matrix multiply. Each weight is loaded once and reused for hundreds of tokens.

Bottleneck: compute (TFLOPS). This is fast: often hundreds to thousands of tokens per second on a GPU.

🐢 Decode (writing the answer)

Tokens come out one at a time, because each new token depends on the previous one. That's a matrix × vector multiply: each weight is loaded and used only once.

Bottleneck: memory bandwidth (GB/s). The cores spend most of their time waiting for weights to arrive.

Worked example (8B Q4 on an RTX 3060): each token reads ~4.9 GB of weights and does ~16 GFLOP of math. The GPU could do that math in ~1 ms (at ~13 TFLOPS), but reading 4.9 GB at 360 GB/s takes ~14 ms. Memory is about 14× slower than the math, so decode speed depends on bandwidth, not core count.

Level 4 · Memory that grows

The KV cache: why long chats eat memory

In attention, each new token "looks back" at every earlier token. To avoid redoing work, the model saves two vectors for every token in every layer: a Key and a Value. That saved data is the KV cache, and it lives next to the weights, in VRAM if possible.

# KV cache size
bytes = 2 (K and V) × layers × KV-heads × head-size × bytes-per-number × tokens

Llama 3.1 8B, FP16 cache:  2 × 32 × 8 × 128 × 2 B = 128 KB per token
   4,096-token context  →  0.5 GB
  32,768-token context  →  4 GB
 131,072-token context  →  16 GB   ← bigger than the model itself!
  • Context length (num_ctx) is how many tokens the model can remember. Ollama reserves KV space for the whole context when the model loads.
  • Raise it with /set parameter num_ctx 16384 in chat, or the OLLAMA_CONTEXT_LENGTH environment variable. More context means more VRAM.
  • Save memory with OLLAMA_FLASH_ATTENTION=1 together with OLLAMA_KV_CACHE_TYPE=q8_0. This stores the cache in 8 bits and roughly halves it.
A classic surprise: a model runs at 100% GPU. You raise num_ctx to 32k, and suddenly ollama ps shows 30%/70% CPU/GPU and speed drops a lot. The bigger KV cache pushed some layers out of VRAM.
Level 4 · Splitting the work

Layer offloading: when the model doesn't fit in VRAM

Ollama's engine (built on llama.cpp / GGML) can split a model by layers. When a model loads, the scheduler:

  1. Checks how much VRAM is free (your desktop and browser already use some).
  2. Works out the memory needed per layer, plus KV cache and buffers.
  3. Puts as many layers as fit on the GPU, and the rest on the CPU + RAM.
ollama ps
NAME           ID            SIZE      PROCESSOR          UNTIL
llama3.1:8b    46e0c10c039e  6.9 GB    100% GPU           4 minutes from now
qwen2.5:32b    9f13ba1299af  22 GB     48%/52% CPU/GPU    4 minutes from now

For each token, the data flows: GPU layers (fast) → a small vector crosses PCIe → CPU layers (slow) → result. Total time = GPU time + CPU time, so the slow part dominates.

A relay race where one runner is a sprinter (GPU) and one is walking (CPU). If the walker has to cover even 30% of the track, the team's time is mostly the walker's time.
Control it yourself with /set parameter num_gpu 20 (the number of layers to put on the GPU). num_gpu 0 forces CPU-only, which is useful for comparing speeds in class.
Level 4 · Performance

Why tokens per second ≈ bandwidth ÷ model size

During decode, every token needs (almost) all the weights read once. So the speed limit is:

max tokens/second ≈ memory bandwidth (GB/s) ÷ model size (GB)
# real-world speed is usually ~60–75% of this limit
HardwareBandwidth8B Q4 (4.9 GB) limitTypical real speed
Laptop CPU, DDR4 dual channel~51 GB/s~10 tok/s~6–8 tok/s
Desktop CPU, DDR5 dual channel~90 GB/s~18 tok/s~10–14 tok/s
Apple M2 (unified)100 GB/s~20 tok/s~14–18 tok/s
RTX 4060 8 GB272 GB/s~55 tok/s~38–45 tok/s
RTX 3060 12 GB360 GB/s~73 tok/s~45–55 tok/s
RTX 4090 24 GB1,008 GB/s~205 tok/s~120–150 tok/s

Numbers are rough and vary with drivers, Ollama version and context length. The pattern is what matters.

Takeaways: (1) A smaller or more quantized model is faster on any hardware. (2) An older GPU with more VRAM bandwidth (RTX 3060, 360 GB/s) can beat a newer one with less (RTX 4060, 272 GB/s) at LLMs. (3) More CPU cores help only until RAM bandwidth runs out, usually around 6–8 cores.

Real world

What happens on common setups

💻 Laptop, no dedicated GPU, 16 GB RAM

Everything runs on the CPU + RAM. 1B–3B models feel smooth (15–30 tok/s), 7–8B models are usable (~5–8 tok/s), and 14B+ is slow.

Best picks: llama3.2:3b, qwen2.5:3b, gemma3:4b.

🎮 Gaming PC, 8 GB GPU (RTX 4060 / 3060 Ti)

7–8B Q4 models fit 100% on the GPU: 35–50 tok/s. 14B models split between CPU and GPU (~8–15 tok/s).

Best picks: llama3.1:8b, qwen2.5:7b; keep the context at ~8k.

🚀 24 GB GPU (RTX 3090 / 4090)

Up to ~32B Q4 models fit entirely in VRAM. 70B models need ~43 GB, so more than half runs on the CPU and it gets slow.

Best picks: qwen2.5:32b, gemma3:27b.

🍎 Mac with 32–64 GB unified memory

No PCIe copy; the GPU can use most of the memory. Mid-range bandwidth, but huge capacity, so 32B–70B models load fine.

Best picks: 14B–32B models; 70B Q4 on 64 GB+.

Upgrade priority for local LLMs

  1. VRAM size: it decides which models run fast at all.
  2. Memory bandwidth: it decides how fast they generate.
  3. System RAM size: the overflow space for bigger models (32 GB is comfortable).
  4. GPU compute and CPU cores: these matter mostly for long prompts (prefill) and many users at once.
  5. A fast NVMe SSD: only affects how quickly a model loads.
Clear the confusion

Common myths

MythReality
"More CPU cores = much faster LLM."Decode is limited by RAM bandwidth. After ~6–8 cores, extra cores just wait for memory.
"The model runs from the SSD."The SSD only stores the file. Weights are loaded into RAM/VRAM first; running from disk would be ~100× slower.
"Shared GPU memory counts as VRAM."Windows' "shared GPU memory" is ordinary system RAM reached over PCIe, which is very slow for LLMs.
"A 7B model needs 7 GB."It depends on the format: ~14 GB at FP16, ~7.5 GB at Q8, ~4.5 GB at Q4, plus KV cache and overhead.
"If it fits in VRAM, context length doesn't matter."The KV cache grows with context. A large num_ctx can push layers back onto the CPU.
"100% GPU usage in Task Manager means it's working well."During decode the GPU is mostly waiting for memory. The utilization number doesn't show that.
