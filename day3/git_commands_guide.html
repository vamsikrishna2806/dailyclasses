Git Commands

The important commands you need every day, with clear examples

1. The Core Idea

Git tracks changes to your files over time. Every change you want to keep is saved as a commit. Files move through three stages:

Working Directory
edit files → Staging Area
git add → Repository
git commit → Remote
git push

2. One-Time Setup

Tell Git who you are. This is stored in every commit you make.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --list

3. Starting a Project

Create a new repository

Run inside an existing folder to start tracking it.

git init

Copy an existing repository

Downloads the full project and its history.

git clone https://github.com/user/repo.git

4. Daily Workflow: Save Your Changes

See what changed

git status          # files changed, staged, or untracked
git diff            # line-by-line changes not yet staged
git diff --staged   # changes already staged

Stage and commit

git add report.txt        # stage one file
git add .                 # stage everything in this folder
git commit -m "Add login page"   # save a snapshot with a message
git commit -am "Fix typo"        # stage tracked files and commit in one step
Good commit messages are short and describe what changed and why, e.g. Add input validation for email field.

5. Viewing History

git log                       # full commit history
git log --oneline           # one line per commit
git log --oneline --graph --all   # visual branch graph
git show abc1234           # details of one commit

6. Branches

A branch is an independent line of work. Use one per feature so main stays stable.

git branch                   # list local branches
git branch feature-login       # create a branch
git switch feature-login       # move to a branch (modern)
git switch -c feature-login    # create and switch in one step
git checkout -b feature-login  # older equivalent of the line above
git merge feature-login       # bring branch changes into the current branch
git branch -d feature-login    # delete a merged branch

7. Working With a Remote (GitHub, GitLab, etc.)

git remote add origin https://github.com/user/repo.git   # connect to a remote
git remote -v                                             # show remote URLs
git push -u origin main       # first push; sets upstream
git push                       # later pushes
git pull                       # download and merge remote changes
git fetch                      # download changes without merging

8. Undoing Things

Discard unstaged edits

git restore report.txt

Unstage a file

git restore --staged report.txt

Fix the last commit message

git commit --amend -m "New message"

Undo a commit, keep the changes

git reset --soft HEAD~1
Be careful: git reset --hard and git restore permanently discard uncommitted work. Commit or stash first if unsure.

9. Temporarily Setting Work Aside (Stash)

Need to switch branches but aren't ready to commit? Stash your changes.

git stash              # save uncommitted changes and clean the folder
git stash list         # see saved stashes
git stash pop          # restore the latest stash and remove it

10. Ignoring Files

Create a file named .gitignore in the project root to keep files out of Git:

venv/
__pycache__/
*.pyc
.env
.ipynb_checkpoints/

Files already tracked by Git must be removed with git rm --cached <file> before they are ignored.

Use Case A: Download a Project and Get Updates (Clone + Pull)

In simple words: Someone else (or you, on another computer) already has the project on GitHub. Clone = download it once. Pull = download only the new changes later.

Step 1: Download the project (you do this only once)

Go to the GitHub page of the project, click the green Code button, and copy the link. Then run:

git clone https://github.com/user/repo.git   # paste your link here

A new folder named repo appears. Enter it:

cd repo                                       # go inside the project folder

Step 2: Get the latest changes (do this whenever you want updates)

git pull                                     # download the newest changes
Remember: Clone is done once. Pull is done again and again.

Special case: "local changes would be overwritten"

What the message means: you have edited files on your computer that are not committed yet, and the same files were changed on GitHub. Git stops the pull so your edits are not lost.

The fix: shelve, pull, bring back

  1. Shelve your edits: git stash  (your files go back to their saved version; your edits are kept on a temporary shelf)
  2. Get the new changes: git pull  (now nothing is in the way)
  3. Bring your edits back: git stash pop  (your edits are applied on top of the new code and removed from the shelf)
git stash          # 1. shelve my unsaved edits
git pull           # 2. download the newest changes
git stash pop      # 3. put my edits back
If git stash pop shows a conflict: the same lines were changed in both places. Open the file, keep the correct lines (Git marks them with <<<<<<< and >>>>>>>), save it, then run git add <file>.
Simpler alternative: if your work is finished, git add . and git commit -m "message" first, then git pull. Git merges both sets of changes for you.

Use Case B: Upload Your Work to Your Own GitHub (Push)

In simple words: You write code on your computer. Push sends a copy of it to your GitHub, so it is backed up and safe. Do this every day.

Step 1: Connect your folder to GitHub (you do this only once)

First, create an empty repository on GitHub (click New on github.com and give it a name). Then, inside your project folder, run:

cd D:\getwork\day3
git remote add origin https://github.com/your-name/your-repo.git
git push -u origin main

Step 2: Every day, do these 4 things

  1. See what you changed: git status
  2. Pick the changes to save: git add .  (the dot means "all of them")
  3. Write a short note about it: git commit -m "Day 3 practice done"
  4. Upload: git push
git status
git add .
git commit -m "Day 3 practice done"
git push
Tip: If git push is rejected saying "updates were rejected", someone else changed the project on GitHub. Run git pull first, then git push again.
Login: GitHub does not accept your normal password here. When asked, sign in through the browser window that opens, or use a Personal Access Token. Never share your token.

12. Best Practices

  • Run git status before every commit.
  • Commit small, related changes with clear messages.
  • Pull before you push to avoid conflicts.
  • Use a branch for each feature or experiment.
  • Never commit secrets (passwords, API keys); keep them in .env and ignore that file.
