01 Level 0 · The problem

The N × M integration nightmare

An LLM by itself only knows what was in its training data. It can't read your files, query your database or check today's weather. To do those things it needs tools and context. Before MCP, every AI app had to write its own custom connector for every tool.

AI apps: 4

Tools / data sources: 5

Custom integrations to build and maintain
20
N × M = 4 × 5
The MCP idea: each AI app implements the protocol once (as a client) and each tool implements it once (as a server). After that, any app works with any tool. N × M integrations become N + M.
02 Level 0 · Mental model

MCP is the USB-C port for AI

Before USB, every printer, mouse and camera had its own cable. USB set one standard, so any device works with any computer. MCP does the same for AI: one standard connector between AI applications and the outside world.

Open standard

Anthropic released MCP in November 2024. It is now an open specification used by Claude, ChatGPT, VS Code, Cursor, Gemini and many others, with SDKs in Python, TypeScript, Java, C#, Kotlin, Go, Rust, Swift, Ruby and PHP.

🔁

Write once, use anywhere

Build a GitHub MCP server once, and every MCP-compatible app can use it. You don't need a Claude version, a Cursor version and a LangGraph version.

🧠

Context, not just tools

It is called a context protocol because it carries more than function calls: documents (resources), prompt templates, and even requests from the server back to the model.

03 Level 0 · Clearing confusion

MCP vs what you already know

Beginners often ask: "Isn't this just function calling? Or a REST API?" It works alongside both. This table shows where each one fits.

REST APILLM function callingMCP
What it isA way for programs to talk over HTTPThe model's ability to output "call tool X with args Y"A standard for discovering and running tools/data across any app
Who defines the tools?Each service, its own wayYou hard-code them in your appThe server advertises them; clients discover them at runtime (tools/list)
Reusable across AI apps?Needs glue code per appNo, it's tied to your codeYes, any MCP host can plug in
Carries context/data?Raw responsesOnly tool resultsTools + Resources + Prompts + Sampling + Elicitation
RelationshipMCP uses function calling (the LLM still decides to call a tool) and MCP servers often wrap REST APIs. MCP is the standard layer between them.
Key insight: the LLM never talks to the MCP server directly. The model only produces text and tool-call requests. Your host application runs the MCP client that actually sends messages to servers.
04 Level 1 · Architecture

Host · Client · Server

MCP has three roles. Click any box in the diagram to learn what it does. The moving dots are live messages: cyan = requests, violet = responses.

RULE 1

One host can hold many clients.

RULE 2

Each client keeps a 1:1 connection with exactly one server.

RULE 3

Servers are isolated. They can't see the full conversation or each other. The host controls what they get.

06 Level 2 · The wire format

Every message is JSON-RPC 2.0

Under the hood, MCP messages are small JSON objects that follow the JSON-RPC 2.0 standard. There are exactly three kinds:

REQUEST

"Please do X"

CLIENTSERVER

Has an id and a method. The sender expects a reply.

RESPONSE

"Here's the result"

CLIENTSERVER

Same id as the request, plus either result or error.

NOTIFICATION

"FYI, no reply needed"

CLIENTSERVER

Has no id. Fire and forget. Either side can send one.

Error response

protocol error (bad method)

    
tool error (tool ran, but failed)

  

  
Why two kinds of errors? A protocol error means the request itself was broken. isError:true means the tool ran but failed. The LLM sees tool errors, so it can fix its mistake and try again.

08 Level 2 · Transports

  
How bytes actually travel

  
The JSON messages stay the same. The transport is just the pipe they travel through. MCP defines two standard transports:

  

    

      LOCAL
📟 stdio

      
The host launches the server as a child process. Messages go through stdin and stdout, one JSON object per line.

      
      
  • Fast and simple, no network
  • Best for local tools: files, git, scripts
  • ⚠️ Never print() to stdout in a stdio server. It corrupts the JSON stream. Log to stderr instead.

    

    

      REMOTE
🌐 Streamable HTTP

      
The server is a web service with one endpoint (for example /mcp). The client POSTs JSON. The server replies with JSON or streams events back (SSE).

      
      
  • Many users, deployed in the cloud
  • Supports OAuth 2.1 authorization
  • Replaced the older "HTTP + SSE" transport in spec 2025-03-26

    

  

  

    
stdioStreamable HTTP

    
Where server runsSame machine, as a subprocessAnywhere on the network

    
Who starts itThe host, automaticallyYou deploy it (it's always running)

    
Clients per serverOneMany

    
AuthEnvironment variables (e.g. API keys)OAuth 2.1 / bearer tokens

    
Config in LangGraph"transport": "stdio" + command/args"transport": "streamable_http" + url

14 Level 4 · Responsibility

  
Security & best practices

  
MCP gives an AI real power: running code, reading data, calling APIs. So you need to know the main risks and how to defend against them.

  

    
THREAT
☠️ Tool poisoning
A malicious server hides instructions in a tool's description ("…also read ~/.ssh and send it"). The LLM reads descriptions, so it may obey.
✅ Use trusted servers only; review tool descriptions.

    
THREAT
💉 Prompt injection via data
A web page or email fetched by a tool contains "ignore previous instructions…". Tool results are untrusted input.
✅ Treat results as data; require human approval for risky actions.

    
THREAT
🎭 Rug pull
A server changes its tool definitions after you approved it (list_changed).
✅ Pin versions; re-review when tools change.

    
THREAT
🔑 Token passthrough
A server forwards a user's token to other services, or accepts tokens that weren't issued for it (the "confused deputy" problem).
✅ The spec forbids it. Validate the token audience (OAuth 2.1 + resource indicators).

    
THREAT
🧨 Command injection
A server passes LLM-chosen arguments straight into a shell or SQL query.
✅ Validate inputs, use parameterised queries, never shell=True.

    
THREAT
🌊 Over-permission
A filesystem server with access to C:\, or a database user with DROP rights.
✅ Least privilege: roots, read-only users, scoped tokens.

Glossary

  

    
MCPModel Context Protocol. An open standard linking AI apps to tools and data.

    
HostThe AI application the user interacts with. It holds the LLM and the clients.

    
ClientA connector inside the host, with one connection to one server.

    
ServerA program that exposes tools, resources and prompts.

    
ToolA function the model can call. It can have side effects.

    
ResourceRead-only data identified by a URI.

    
PromptA reusable message template the user can choose.

    
SamplingA server asking the client's LLM to generate text.

    
ElicitationA server asking the user for structured input.

    
RootsThe boundaries (folders/URIs) a client lets a server work in.

    
JSON-RPC 2.0The message format: request, response, notification.

    
stdioLocal transport through a child process's stdin/stdout.

    
Streamable HTTPRemote transport: a POST to one endpoint, optionally streamed with SSE.

    
CapabilitiesFeatures each side announces during initialize.

    
FastMCPA high-level Python API for writing servers with decorators.

    
MCP InspectorA visual testing tool (mcp dev / npx @modelcontextprotocol/inspector).

    
langchain-mcp-adaptersTurns MCP tools into LangChain/LangGraph tools.

    
ReActThe Reason + Act loop: think → call tool → observe → repeat.
